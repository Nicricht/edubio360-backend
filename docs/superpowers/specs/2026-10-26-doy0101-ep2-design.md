# EP2 DOY0101 — Diseño de integración DevSecOps

## Propósito

Usar el backend Java 21 de EduBío 360 como proyecto existente para demostrar los cinco indicadores de la evaluación DOY0101: contenedores, pruebas, seguridad, despliegue simulado y orquestación. La pauta oficial `EP2_DOY0101_Estudiante.pdf` prevalece sobre material de orientación y sobre la documentación de la EP02 de JVY0101 presente en este repositorio.

## Alcance y límites

- Conservar los ocho módulos Maven, los seis servicios de negocio, Gateway, Eureka, MySQL y RabbitMQ. No rediseñar lógica de negocio ni cambiar tecnología.
- Usar GitHub Actions para el flujo completo y Docker Compose en el runner como **entorno simulado efímero**, no como alojamiento persistente en la nube.
- Conservar la compilación con Java 21 y las pruebas Maven/JaCoCo; no sustituirlas por ejemplos Python.
- Añadir Dependabot, análisis SCA/SAST con Snyk y bloqueo verificable antes de construir/desplegar. El token debe configurarlo un integrante como secreto `SNYK_TOKEN`; no guardarlo en Git.
- Mejorar contenedores con usuario sin privilegios, límites de recursos y comprobaciones de salud, sin prometer alta disponibilidad que Compose no aporta.
- Marcar imágenes con el SHA del commit y publicar evidencias de ejecución (test, cobertura, seguridad, despliegue).
- Documentar comandos y ubicación de la evidencia; no redactar conclusiones, justificaciones técnicas personales ni reflexiones individuales que exige elaborar el alumnado sin IA.

## Alternativas consideradas

1. **Reforzar el monorrepositorio existente (seleccionada):** aprovecha CI, pruebas y Compose reales. Tiene más módulos que un ejemplo simple, pero permite evidenciar el sistema trabajado anteriormente.
2. Extraer un único microservicio: reduce tiempos de CI, pero pierde una parte significativa de la orquestación ya construida y duplica infraestructura.
3. Desplegar a una nube persistente: permite una URL permanente, pero incorpora cuentas, costes, secretos y operaciones adicionales que la pauta no exige frente al entorno simulado.

## Flujo propuesto

1. `verify`: `mvn clean verify`, sintaxis Compose, reportes de prueba y cobertura.
2. `security`: Snyk Open Source sobre el agregado Maven y Snyk Code, sin `continue-on-error`; Dependabot mantiene los manifiestos.
3. `image-build`: construir una imagen verificable y etiquetarla con el SHA.
4. `deploy-smoke`: `docker compose up -d --build` y smoke tests existentes; conservar logs y reportes. El entorno del runner se destruye al terminar.

Los jobs de build y despliegue dependen de pruebas y seguridad. En PR externos sin acceso a secretos se evita ejecutar contenido no confiable con un token privilegiado y no se permite desplegar.

## Criterios de aceptación

- Los manifiestos YAML validan; cada job expresa dependencias y privilegios mínimos.
- Una vulnerabilidad por sobre el umbral configurado o un error de escaneo impide el despliegue en ejecuciones confiables.
- Las imágenes se construyen desde un Dockerfile multi-stage con usuario no root; Compose conserva MySQL/RabbitMQ y añade recursos/healthchecks.
- El build y el smoke test se verifican en un runner con Java 21 y Docker; la validación estática local no sustituye dicha evidencia.
- README documenta la forma de ejecutarlo y las evidencias por IE1–IE5, además de la obligación de declarar asistencia de IA.

## Riesgos

- La ejecución de Snyk requiere una cuenta y un secreto configurado por el equipo; sin él debe fallar claramente, no aparentar aprobación.
- El runner Linux puede quedarse sin memoria si los límites/reservas exceden su capacidad. Los valores deben probarse con la pila completa antes de declararlos válidos.
- Los puertos de host fijos impiden escalar varias réplicas del mismo servicio sin reconfiguración. El diseño prioriza estabilidad de la composición; la escalabilidad adicional requiere una decisión explícita.

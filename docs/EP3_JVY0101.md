# EP3 JVY0101: integración y despliegue de soluciones cloud

La entrega reutiliza los seis microservicios Java, Eureka, Gateway, MySQL y RabbitMQ de EP2. No es necesario reemplazar MySQL por Oracle. Los datos de prueba del catálogo son demostrativos; no se presentan como oferta vigente.

## Arquitectura propuesta e implementada en código

Cliente HTTPS → AWS HTTP API → ALB interno → Spring API Gateway → Eureka y servicios en Docker Swarm.
Guidance publica la confirmación en RabbitMQ. Notification procesa su cola original; una segunda cola durable alimenta el puente de eventos, que publica únicamente el ID de solicitud en SQS. Lambda consume SQS y almacena una constancia idempotente en DynamoDB. La cola SQS tiene DLQ. No se envía correo externo ni se exportan correos personales a SQS.

Swarm tiene un manager y un worker EC2, red overlay y solo el puerto del Gateway publicado en el clúster; EC2 no acepta tráfico directo de Internet. Los contenedores de negocio comparten MySQL mediante seis bases lógicas. Los datos y Eureka se fijan al manager: esta solución demuestra distribución y escalado, no alta disponibilidad de la base ni del plano de control. La cuenta de DB root en red privada se conserva por compatibilidad EP2; para producción separar usuarios por base, secretos, backups y tres managers. La configuración cloud activa restricciones adicionales por rol en Gateway. No sustituye una autorización exhaustiva por objeto. Los nodos comparten rol IAM de EC2 para SSM, ECR y acceso mínimo a la cola y constancias. La etiqueta SHA permite trazabilidad. La imagen usa dos etapas y UID 10001.

## Local (Bash, Docker Desktop Linux o WSL)

Desde la raíz, construir imágenes y ejecutar la composición habitual de EP2 para comprobar todos los endpoints locales. Detenerla sin eliminar datos antes de Swarm (puerto 8080 ocupado).

    export IMAGE_PREFIX=edubio360 IMAGE_TAG=local
    export MYSQL_ROOT_PASSWORD=$(openssl rand -hex 24)
    export RABBITMQ_PASSWORD=$(openssl rand -hex 24)
    export JWT_SECRET=$(openssl rand -hex 48)
    bash scripts/ep3/build-images.sh
    bash scripts/ep3/swarm-init.sh manager
    bash scripts/ep3/swarm-deploy.sh
    bash scripts/ep3/swarm-smoke.sh
    bash scripts/ep3/flow.sh

Conservar las tres contraseñas para reiniciar sin perder acceso a los volúmenes. Para incorporar un worker, en el manager ejecutar docker swarm join-token worker y copiar el token de manera privada a otra máquina alcanzable por red; ejecutar el script swarm-init.sh worker IP_MANAGER con SWARM_JOIN_TOKEN definido. Verificar docker node ls, docker stack services edubio, docker service ps edubio_analytics-service y docker service scale edubio_analytics-service=2. Volver a 1 tras la demostración. El smoke automatizado verifica todas las sondas privadas, documentos OpenAPI, HTTP 401 y réplicas. El flujo crea un estudiante y un orientador temporal, comprueba HTTP 403, confirma solicitud y verifica la notificación. Los comandos crean registros de prueba; ejecutar solo en entorno académico aislado.

## AWS y CI/CD

Workflow .github/workflows/ep3-cloud.yml: Maven y pruebas Python → construcción de las ocho imágenes Java + puente → Swarm en runner → gate de seguridad → aprovisionamiento CloudFormation → publicación ECR → despliegue en ambos nodos vía SSM → prueba de extremo a extremo por HTTPS. El runner temporal de Swarm tiene un solo nodo; los dos nodos reales corresponden a AWS. Configuración inicial única, por el dueño de AWS: establecer una identidad OIDC de GitHub Actions limitada al repositorio y entorno ep3-aws, autorizada a administrar los recursos de cloud/infra.json, incluyendo PassRole para los roles de la pila, ECR y SSM. Crear entorno GitHub ep3-aws; variables del repositorio EP3_AWS_REGION (p.ej. us-east-1), EP3_AWS_ROLE_ARN, EP3_AWS_ENABLED=true y secreto SNYK_TOKEN. Restringir confianza OIDC al subject repo:Nicricht/edubio360-backend:environment:ep3-aws y audience sts.amazonaws.com; proteger el entorno para que solo permita ramas autorizadas. No colocar claves de acceso en Git.

Antes de habilitar AWS, autorizar costo: dos EC2 t3.large, discos, IP públicas, ALB, ECR, Lambda, SQS y DynamoDB pueden generar cobros. La plantilla crea VPC propia y requiere dos AZ. El job cloud no se activa por defecto. El gate Snyk no acepta excepciones vencidas; la CVE JAXB de EP2 debe resolverse o revisarse formalmente antes de un despliegue público. No modificar su fecha para forzar el aprobado. Si el despliegue falla, revisar Actions y CloudFormation Events. Tras la evaluación eliminar la pila edubio-ep3 con CloudFormation solo tras confirmar que se pueden borrar sus datos y exportar evidencias; si se recrea el clúster se pierde la base local del manager. La autenticación ECR es temporal y se renueva al desplegar; para operación prolongada automatizar renovación.
